# 竞品监测周报合集 · 协作工作流

> 站点：`https://xmonitor.doc.nie.netease.com/competitor-weekly/`
> 仓库：`gitlab.nie.netease.com/xmonitor/xmonitor.doc.nie.netease.com`，目录 `competitor-weekly/`
> 机制：纯静态 Pages，**改 data/*.json → push main → CI 自动发布**，无后端、无需改代码
> Agent 数据格式细节见同目录 `AGENT.md`（本文不重复字段规范）

---

## 一、角色分工（按模块认领，互不等候）

| 角色 | 负责内容 | 负责文件 | 更新频率 |
|---|---|---|---|
| A · 周报框架负责人 | 新周期建档、首页综述、发布总控 | `reports.json`、`periods.json`（建当期框架 + `overview`）、`app.js` 的 `state.period`（唯一代码改动） | 每周一 |
| B · 数据负责人 | 各产品流水/DAU/峰值及环比、日级数据 | `periods.json`（当期 items 数值）、`daily-metrics.json` | 每周 |
| C · 核心运营内容负责人 | 详情页「核心运营内容」正文与配图 | `core-items.json`、`core-images.json` | 每周 |
| D · 首页卡片与亮点负责人 | 异动卡片情报、数据表亮点短句、状态标记 | `intel.json`、`hero-event-summaries.json`、`periods.json`（当期 items 的 note/keywords/status） | 每周 |
| E · 画像与归档负责人 | 用户画像、历史周报归档 | `audience-profiles.json`、`archive-reports.json`、`archive-periods.json`、`archive-content.json` | 按需 |

> 人数少时可一人兼多角；文件归属即责任边界，**只改自己负责的文件**。

## 二、每周时间线

```
周一上午   A 拉最新代码 → 建新周期框架（reports + periods 新 key + state.period）→ push
周一下午   B/C/D 并行开工（互不等待，各改各的文件）
周二~周三  C 补核心运营正文与配图；E 按需补画像/归档
周三下班前 各自完成 push；A 线上抽查各模块
周四       发现问题 → 责任人小改 → 直接 push（同流程）
```

## 三、每个角色的标准操作（含 Agent 用法）

所有角色同一套骨架，只是改的文件不同：

```bash
# 0. 首次：克隆；非首次进仓库目录即可
git clone https://gitlab.nie.netease.com/xmonitor/xmonitor.doc.nie.netease.com.git
cd xmonitor.doc.nie.netease.com

# 1. 动手前必做：同步线上最新版
git pull --rebase origin main

# 2. 把素材 + AGENT.md 对应章节发给 Agent，产出新 JSON 内容
#    提示词模板：
#    「阅读 competitor-weekly/AGENT.md 第 4 节。
#     这是当前文件 <贴入 data/xxx.json>，这是我的本周素材 <贴素材>。
#     按规范只更新 <你的产品/模块> 部分，未知指标填 null，输出完整合法 JSON。」

# 3. 用 Agent 产出替换对应文件后，本地校验
node -e "JSON.parse(require('fs').readFileSync('competitor-weekly/data/xxx.json','utf8'));console.log('ok')"

# 4. 只提交自己改的文件
git add competitor-weekly/data/xxx.json
git commit -m "周报更新 2026MMDD：<角色/模块>（姓名）"

# 5. push 前再同步一次（防同事并发），无冲突后推送
git pull --rebase origin main
git push origin main
```

push 后约 1-2 分钟线上生效，强制刷新（Ctrl+F5）查看。

### 各角色差异点

**A · 周报框架（每周先做，他人依赖）**
1. `reports.json` 数组最前插入新一期；`periods.json` 复制上期 key 改为本周一日期，items 数值先置 `null`
2. `app.js` 顶部 `const state={period:'20260622',...}` 改为新 key（**全项目唯一允许的代码改动**）
3. 当期 `overview`（本期综述）写好
4. 第一时间 push，并在群里通知「框架已建」

**B · 数据**：只动 `periods.json` 当期 items 的数值字段与 `daily-metrics.json`；`null` 不许编。

**C · 核心运营内容**：
- 正文按 `○`主题/`–`要点/`·`细节/`“`引用 层级写进 `core-items.json` 对应产品数组
- 配图转 base64 webp 放 `core-images.json`，正文按现有条目格式引用 key
- 图片较多时用脚本辅助转码，不要手贴几 MB 的 base64

**D · 卡片与亮点**：改 `intel.json`；数据表「运营亮点」短句是 `app.js` 里的 `HIGHLIGHT_SHORT` 映射——如需改文案，**只改该常量**，并在 commit 注明。

**E · 画像/归档**：归档三件套（reports/periods/content）必须**同 key 一起加**，否则详情页缺数据。

## 四、并行不冲突的规则

1. **文件级隔离**：B/C/D/E 的文件互不重叠，天然无冲突；A 的框架文件（reports/periods）在周一上午独占，他人下午再动。
2. **唯一共享文件 `periods.json`**：A 建框架、B 填数值、D 填 note/status。约定：A 周一上午 push 后，B、D 同日改时**必须 pull --rebase 后再 push**；rebase 出冲突时，保留双方改动（A 的框架 + 你的字段），不会处理就把冲突文件发群里 @对方。
3. **禁止事项**：不改他人负责文件；不 `git add -A`；不用 `--force` push；不编数据。

## 五、出错了怎么办

| 情况 | 处理 |
|---|---|
| push 被拒（fetch first） | `git pull --rebase origin main` 后再 push |
| rebase 冲突 | `git status` 看冲突文件 → 手动合并保留双方内容 → `git add` → `git rebase --continue`；不会就 `git rebase --abort` 回退再找人 |
| 改错已 push | 不要 force push。`git log --oneline` 找到错误提交 → `git revert <sha>` → push |
| 线上 404/没更新 | 等 2 分钟 Ctrl+F5；确认 CI 完成（GitLab → CI/CD → Pipelines 绿色）；确认改的是 main 分支 |

## 六、验收（每人 push 前）

- [ ] 先 pull --rebase 拿到最新版再改的
- [ ] 改动的 JSON 已通过 `JSON.parse` 校验
- [ ] 只 add 了自己负责的文件（`git status` 复核）
- [ ] 未知数据是 `null`，无编造
- [ ] push 前再次 pull --rebase 无冲突
- [ ] push 后 2 分钟线上核对了自己负责的模块
